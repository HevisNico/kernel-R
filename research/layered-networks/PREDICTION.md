## 2. The primary claim: a direct test

For each instance, before any network run (stage D, same deck and seed, so the same devices):
- every R cell is measured alone (scans from the preset, the family's order, repeat rule v2), fitted, and gated at K0 and K3 (`fit3`, one-port rule for the either cell; DECISIONS_3.md). The Lean kernel has the last word on Cell.Valid (LayeredMonotoneTarget.lean), clause by clause (`leancell.py`, stage_d6); the exact-arithmetic Python mirror is reported beside it, and a disagreement is a run failure ("not completed"). The training and read calibration clauses are checked by the mirror only. Before the freeze the kernel agreed with the mirror on all 7,826 clause theorems of the 95 sealed predictions available (yield lot, dry runs, D4 check, a forced D4 regate) [K, KERNEL_RCELLS.md];
- every inverter is gated in the network deck itself (`invinst.indeck`, CircuitInverterGate.lean, K0, K3, StateBound);
- the prediction is written and sealed (sha256 manifest, ENV.json hash included): every training word, every output on all 2^m patterns, every cell bit, the skew slots' silence, eligibility at K0 and room at K3.

**Sealing (fixed now).** (a) Each instance's prediction is sealed BEFORE its own stage N starts. (b) The sealed prediction leaves the machine before that stage N starts: in one append-only commit on its own log branch `evidence/combined-seals-K<nn>`, the machine appends a line (instance, seal sha256, UTC time) to SEALS.txt and adds the full sealed folder `seals/<inst>/` (every file its SHA256SUMS lists, a few kB), then pushes it plainly (`sealpush2`); stage N starts only after the push succeeds. A second seal of the same instance is refused. The push time is the one GitHub records, not the commit date. GitHub records the first push of a log branch as a branch creation, and that event counts as its push; a force push or a branch deletion never gives a seal its time. The analysis reads push times from GitHub's record only (`times=github`), and saves the raw activity items of every seal-log branch with its results; if GitHub cannot answer on the day of the analysis, the analysis refuses and is rerun when it can, never reinterpreted. The coordinator's ls-remote log (polled every 20 s, too coarse for margins of about 3 s) is a cross-check outside the analysis, never a source of times. The stage-N start time each margin is measured against is the machine's own record (status.json). The coordinator verifies every log after the campaign against the stage-N start times recorded on the machine. Stage N refuses to start without the seal-log commit, and records that commit in every stage-N record. A stage N with no seal pushed before it counts as not sealed and has no prediction. A duplicate machine fetches the log branch by name and checks that the commit is on the branch, that the SEALS.txt line equals the sha256 of the folder's SHA256SUMS, and that the seal verifies, before it writes its own comparison. (c) The one analysis regenerates every prediction from the stage-D records alone, on a machine other than the one that ran the instance, and checks it byte-identical to its seal. A mismatch is reported as a defect and that instance has no counted prediction.

Then stage N, the network trained by its own pulses and tested on every pattern, is compared **directly** with the sealed prediction.

- **K0 (no noise)**: on every eligible instance, one run. **One differing letter, cell bit or output refutes.**
- **K3 (noise)**: on every instance with room, 3 noisy runs (rounds 1–3, noise seed 10·S + n), each predicted to train and answer as sealed. **One difference refutes.**
- **No prediction, no claim.** A run on an instance without eligibility (K0) or without room (K3) is reported plainly as observed. It is never "predicted to fail", and it counts for no claim and no refutation.
- **Complementary analysis, announced now and run after the campaign (not part of the frozen analysis).** On the kept stage-N records (and the kept trace data of §7), a separate tool, written after the campaign, applies the kernel's recognition theorem (`layered_recognition_at`; `layered_inverters_chained` for G1 and G3) and checks the three premises that the frozen analysis does not check: the leak along the trajectory, the latch delay, the routed walk. Its role is fixed now:
  - it can only flag an instance, and so only lower a count; it can never remove a refutation or add a held instance;
  - the report gives every count in two versions, without and with these flags.
  - it also lists the GitHub activity of every seal-log branch by type, and reports any force push or branch deletion there (a flag only, under the same two rules).

## 4. "Established" (fixed before any data)

A counted instance: eligible (K0) or with room (K3), fixed by stage D (§8 failure rule). The thresholds below count HELD instances: counted, completed, every comparison agreeing, no premise flagged. Per group and level:

| Level | refuted | established | held on k instances, not established | held on one instance | not established |
|---|---|---|---|---|---|
| K0, G1 | ≥ 1 refutation, whatever k | ≥ 30 and no refutation | 2 ≤ k < 30, no refutation | 1, no refutation | 0, no refutation |
| K0, G2 and G3 | ≥ 1 refutation, whatever k | **≥ 20** and no refutation | 2 ≤ k < 20, no refutation | 1, no refutation | 0, no refutation |
| K3, every group | ≥ 1 refutation, whatever k | ≥ 5 and no refutation | 2 ≤ k < 5, no refutation | 1, no refutation | 0, no refutation |

- **A refutation prevails over every count:** one counted instance whose comparison differs (or that the failure rules of §8 count as refuted) gives its group and level the verdict `refuted`, whatever k: 20 held XOR3 instances at K0 and one differing give `refuted`, not `established` (`analysis.word`).
- **All three groups together** ("NOT, layers without NOT, and layers with NOT"): at a level, `refuted` if any group is refuted; established only if each group is; otherwise worded per group (`analysis.family_of`).
- P(not established | every prediction right) [I, binomial, at the lot rate / at its lower 90 % bound]:

| | G1 K0 | G1 K3 | G2 K0 | G2 K3 | G3 K0 | G3 K3 |
|---|---|---|---|---|---|---|
| P(not established) | ≈ 0 / ≈ 0 | ≈ 0 / ≈ 0 | ≈ 1 % / ≈ 40 % | ≈ 63 % / ≈ 98 % | ≈ 0 / ≈ 0.5 % | ≈ 3 % / ≈ 43 % |

Stated plainly: at the lower bounds, G2 at K0 and G3 at K3 may well end "held, not established"; G2 at K3 is expected not established.

## 8. Premises, decisions and expectations, stated in advance

- **Open premises, assumed, not proved** (the claim reads "computes f under these premises"): the leak along the trajectory (one of two fitted side rates at each time); the simulator's measured real hypotheses, supplied as outward-rounded numbers; the latch delay (measured, not bounded); the routed walk (checked per trace, no soundness proof); D4 (`d4_stage` 0.005, audited on every 6th instance).
- **Rule decision recorded:** the either cell uses the one-port test budget (campaign (a)'s family rule), adopted on 2026-11-24 after dev failures were seen (DECISIONS_3.md, 70fad23), before the freeze. **Declared comparison, counting for nothing:** room and eligibility under the superseded max rule, reported beside the claims.
- **Expectations:** the either cells and the inverter-fed outputs are the noisy ones. If a noisy run refutes, the either cell's two-port read is checked first (PLAN_NOTES_3.md). The injected noise model is pessimistic: 262 µV injected against 66 µV for the device model on a read of the stored voltage, and 1.7 to 1.8 times the drift of a read (research/circuit/DESIGN.md; research/network-noise-study/phase0/FEASIBILITY.md). The yields are measured (§3): at K3, G2 is expected not established, so "all three groups together" at K3 is expected not established either.
- **Failure rule (the owner's decisions, before the freeze).**
  - **Not completed.** A step that crashes (a simulator end or a failure other than a noisy run's own check, which is refuted, below), hits its time limit or is interrupted (found running at a resume), from stage D to stage N, ends that instance's run at that level as "not completed". It is neither a refutation nor a hold. It is listed with its seed, its step and its reason, never re-run and never replaced, and it counts for nothing, for or against. The per-step time limits (`campaign_template.json` time_limits_s, in s): deck 120, inverters 3600, stage D 7200, seal 120, each stage-N round 7200, comparison 300, U 3600, duplicate 7200; at the limit the step's process group is killed and the step recorded "timeout" with its wall and CPU time; a step found running at a resume is recorded "interrupted". None was hit in the pre-freeze dry runs (the longest stage-N round measured: 63 CPU-min).
  - **The counted set is fixed by stage D, before stage N:** eligibility at K0, room at K3, the inverter gates. Nothing observed during or after stage N removes an instance from it. The two levels are counted separately: an instance's K3 count depends on its room at K3 and its noisy rounds only, not on its K0 result.
  - **A seal commit without a push time.** In campaign mode a seal commit to which GitHub gives no push time refuses the analysis (a slow API: rerun later). If it can never be timed (a rewritten seal-log branch), that case is settled by a written amendment, published in the open, never silently.
  - **A completed run left uncompared.** If the driver stops during a comparison step (recorded "interrupted", never relaunched), that round is "not completed" and listed with the step; it is compared by hand with the pinned compare_d2 in the complementary analysis and reported there.
  - **The draw cannot be redone.** The analysis refuses if the announcement branch was ever force-pushed or deleted, requires the announcement commit to be the one that created that branch, requires the announcement to have been pushed after the frozen tree, and refuses if any drawn instance was sealed before the draw. The rehearsal shares the campaign's seal-log branches; its seeds enter the exclusion list by the second scan, which reads every branch including the seal logs and is required before the draw. The campaign's exclusion list is the second scan's output plus every rehearsal seed and its four noise seeds (the scan alone cannot find them all: round 0 has no noise seed written anywhere), built by the three commands given in FREEZE.txt: add, for each of the 18 seeds S of the verified rehearsal draw, S and 10 S + n for n = 0..3 to the second scan's output; deduplicate, sort and regenerate EXCLUDED.json with its count and internal sha256; re-read the final file, check that the 18 seeds and their 72 noise seeds are in it, and only then write that exact file's sha256 into the announcement. The analysis re-reads the rehearsal's own verified public draw and refuses the campaign if any of its 18 seeds or their noise seeds is missing from the campaign's announced exclusion list, or if the rehearsal's announcement is not earlier than the campaign's (the owner's finding, 2026-11-27, before the freeze). Each announcement branch (the rehearsal's and the campaign's) is single-use: it is created by one push whose tip adds DRAW_ANNOUNCE.txt in its fixed format, checked locally before that push, and is never deleted or recreated; a mistake there means a new freeze. The frozen tree is pushed on research/layered-campaign-freeze before either announcement.
  - **The draw is recomputed in full.** The analysis verifies the beacon round's signature against the pinned chain (randomness = sha256(signature)), recomputes the round from GitHub's push time of the announcement commit, recomputes every seed with the pinned `draw_seeds.py` from that value, the round, the sizes pinned in `analysis.py` (60, 32, 37) and the published exclusion list (its sha256 announced before the round, a superset of the one frozen here), and requires the published DRAW.json to equal it byte for byte.
  - **Every drawn instance is accounted for.** The analysis rebuilds every machine's plan from the recomputed draw with the pinned splitter and refuses a root whose plan differs; every planned instance receives a state (held, refuted, not completed with its step, not run, not sealed); a drawn instance with no run is listed "not run" (it counts for nothing) and is looked up in its machine's seal log; a machine that stopped early keeps every result it has: a completed comparison that differs counts refuted even if the rest of that machine's runs are missing (flagged "manifest not final"; it must recompute byte for byte with the pinned compare_d2 from the sealed prediction and the run's record, and match the hashes the machine recorded for that step; this anchors only what the machine wrote, so it is used only where it can lower a count: an agreement is never counted without the final verified manifest); an unfinished root is finished by resuming its driver, and no root is ever left out; a repeated root, machine or instance refuses, and every file the analysis reads is checked against its manifest line (or is on a short list named in the code), a mismatch refusing the analysis.
  - **Refutation.** On a counted instance, one differing letter, cell bit or output in a completed comparison refutes, whatever premises are observed in stage N. A false premise found beside it is reported as the diagnostic, never as an excuse. A defective seal never removes a refutation: a completed comparison that differs stays refuted and is flagged "seal defect"; only an agreement needs a valid seal (the owner's decision, 2026-11-27, before the freeze).
  - **A run stopped by its own check is refuted.** A noisy network run that stops on one of its own checks because of what the circuit did (for example a cell already latched, an emission too late to schedule the next pulse; status "failed: …" in its record, as opposed to a simulator crash or a time limit) did not produce the predicted letters: it counts as refuted, in its own sub-row "stopped by the run's own check", and its trace is kept for the complementary analysis, which can never remove the refutation (the owner's decision, 2026-11-27, before the freeze). The record keeps only the error's message, not its type, so a software error inside the run reads the same way and also counts as refuted: this errs toward refuting, never toward holding; the analysis lists every such stop with its full message.
  - **Premise flagged.** In the frozen analysis, the only premise checked during the campaign is D4 (below): an instance flagged by the D4 rule does not count towards "established" at that level; it is reported apart, with the clause; it is not a refutation. The leak along the trajectory, the latch delay and the routed walk are assumed, not checked by the frozen analysis; the complementary analysis of §2 checks them afterwards, under the two rules stated there.
  - **Counts reported side by side (`analysis.py`):** per group and level, counted, held, refuted (with its sub-row "stopped by the run's own check"), not sealed, premise flagged (D4), not completed (with the failing step) and not run, summing to the drawn size, so that a group cannot look clean because its hard instances did not finish.
- **Zero-noise identity (a check of the environment, criterion fixed by the owner before the freeze, `check_noise_identity2`):** noise sources at amplitude 0 must give the same words, lessons, tests, skews and emissions as noise off, with u equal to ±1 in the record's last digit; latch dates (−4 to +17 ns seen) and inverter x readings are listed, not judged.
- **D4 (the stage-D/network scan difference), audited, rule fixed by the owner before the freeze (`analysis.py`, `d4_regate.py`).** Every 6th instance of each group in draw order runs its stage D with solo scans; on it, the measured value replaces the constant 0.005 in its own budgets (fit.py). The constant 0.005 is the maximum of six 2x measurements rounded up; twelve 2x measurements exist before the campaign, all below it (max 0.00405), the twelfth from the end-to-end audit check of 2026-11-25 (NOT1 6220, 0.00397) [K]. The analysis reports every audited cell line against 0.005. Per group, D4* is the largest audited value; if D4* > 0.005, every unaudited instance of that group is regated from its sealed stage-D record with D4* in place of 0.005, at K0 and K3, without simulation; one whose gate then fails at a level is "premise flagged" there (not counted towards established, reported). The sealed predictions are never modified and nothing removes a refutation. This still assumes the unaudited instances are no worse than the worst audited one of their group.
- **Known limits carried:** G2's shared first-layer stimulus (the Lean witness uses separate stimuli); the either cell's two inputs are driven together in stage D (offset 0) but arrive up to about 0.7 tu apart in the network (covered by the routed-walk premise); one ngspice convergence line per run; the router's 0.02 tu grid; the inverter x_D reading written by the network runs is a linear interpolation at T+D−2 ns and can be wrong next to a reset edge (one artifact in 468 dev readings, on a fired slot); no gate, margin, prediction or comparison reads it;  the 200 ns maximum step in the network against 5/20 ns in the inverter characterisation (no effect observed on 9803); numpy 2.5.3 used for some dev in-deck gates (verdict-identical to 2.3.5, not byte-identical); the yield lot's ENV.json on 11 of 12 machines hashes the elan proxy, not the Lean binary (version 4.35.0 checked; the lot fixes sizes only); the seal margin compares GitHub's clock with the machine's (a machine clock running more than about 3 s behind GitHub would make its instances "not sealed": never a false seal, but a lost share; checked at the rehearsal); simulation only (one simulator, one corner, injected noise, no parasitics, no silicon).

## 9. Order of steps

Pre-freeze dry runs (done 2026-11-25: XOR3 9803 one clone; NOT1 9804 two clones, after fixes; ANDOR3 6104 two clones; a NOT1 D4 audit end to end; and one final dry run of the complete final chain through the pinned template, NOT1, XOR3 and ANDOR3 with the kernel, a remote duplicate and the extract) → integration branch → one driver, one analysis, one template on research/layered-campaign-dev, with equivalence tests (a), (b) and (c) and the fix (b) found → freeze commit (with the beacon rule of §7) → CI at the freeze → this file pushed alone → rehearsal on 12 machines from the pinned campaign template: 18 instances (6 per group, fixed in `analysis.py`), with a D4 audit on the 6th instance of each group in draw order, a draw at the drand round fixed by the rehearsal's own announcement on `evidence/combined-rehearsal-draw` (the historical round 1000000 is used by the offline tests only), analysed in the analysis's rehearsal mode, which applies every campaign check (exercises the seal pushes of §2 on GitHub and must show, for each group, a sealed and counted instance, and a remote duplicate judged by check_duplicate on GitHub; it reports the smallest seal margin per machine (GitHub's push time against the machine's stage-N start, about 3 s by design), and a machine whose margins sit well below the others' has its clock put right before the draw; costs them; fixes the machine count and the window; the sizes are final) → draw announcement pushed alone, then the seed draw at the round of §7, published → campaign, blinded, with each seal pushed before its stage N → one analysis, with the seal regeneration on another machine → report → PR.
